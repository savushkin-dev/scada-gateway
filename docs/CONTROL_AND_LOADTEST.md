# Управление с монитора и нагрузочное тестирование

Инструкция по двум возможностям шлюза:

1. **Управление контроллерами с монитора** — оператор пишет значения в ПЛК (выключить
   мотор, открыть клапан, задать уставку), но только туда, куда физически можно писать;
   показание датчика изменить нельзя.
2. **Нагрузочное тестирование** — стенд, который гоняет систему под нагрузкой и снимает
   метрики (стресс / волна / soak).

---

## Часть 1. Управление контроллерами с монитора

### 1.1. Как это работает

```
 Монитор ──(команда)──▶ scada-commands ──▶  ШЛЮЗ  ──(запись)──▶  ПЛК (OPC UA / PAC)
    ▲                                          │
    │                                          ▼
    └────(результат)──── scada-command-results ┘

 …а изменённое значение возвращается штатной телеметрией:
    ПЛК ──▶ ШЛЮЗ ──(телеметрия)──▶ scada.tags ──▶ Монитор
```

- Монитор шлёт команду в топик `scada-commands`.
- Шлюз (`CommandConsumer`) её принимает, находит тег по имени, проверяет право на запись
  и пишет значение в контроллер тем протоколом, которым тег читается (OPC UA или PAC —
  решает шлюз, наружу это не торчит). Modbus-контроллер (WAGO) только на чтение.
- Результат уходит обратно в `scada-command-results` — монитор коррелирует его по `commandId`.
- Новое значение приходит оператору обычной телеметрией в `scada.tags`.

### 1.2. Топики — единая точка стыка шлюз ↔ монитор

Все три топика **общие** и заданы в шлюзе в `application.yaml → kafka.topics`, а в мониторе
в `runtime → KafkaProperties`:

| Назначение | Топик | Направление |
|---|---|---|
| Телеметрия | `scada.tags` | шлюз → монитор |
| Команды | `scada-commands` | монитор → шлюз |
| Результаты команд | `scada-command-results` | шлюз → монитор |

> ⚠️ Имена топиков должны совпадать с обеих сторон. Если менять — менять в шлюзе
> (`kafka.topics.*`) и в мониторе (`KafkaProperties`) одновременно.

### 1.3. Контракт команды

**Команда** (монитор → `scada-commands`, key = имя тега):

```json
{
  "commandId": "3f2b8c14-9d05-4e77-8a1b-6c2e0f4d7b93",
  "tagName":   "Барановичи-1.BN1_MCA1.V_ST_1.LINE1V0.ST",
  "value":     true,
  "requestedBy": "scada-runtime",
  "timestamp": "2026-08-06T12:27:00Z"
}
```

- `tagName` — **полный путь тега** (он же Kafka-key телеметрии). Единственный адрес тега.
- `value` — типизированный скаляр: `bool` / `number` / `string`.
- Поля `dataType` **нет намеренно** — тип точки знает только шлюз (из конфигурации тега).
  Ключ команды тоже = путь тега (упорядочивание команд по одному тегу), но адрес берётся
  из тела: команда без ключа всё равно доедет.

**Результат** (шлюз → `scada-command-results`, key = имя тега):

```json
{
  "commandId": "3f2b8c14-…",
  "tagName":   "Барановичи-1.BN1_MCA1.V_ST_1.LINE1V0.ST",
  "status":    "APPLIED",
  "success":   true,
  "message":   "Записано значение true",
  "appliedValue": true,
  "timestamp": "2026-08-06T12:27:00Z"
}
```

**Статусы** (`CommandStatus` в шлюзе; монитор различает их без разбора текста):

| Статус | Что значит |
|---|---|
| `APPLIED` | Записано и подтверждено контроллером |
| `REJECTED_UNKNOWN_TAG` | Тега с таким именем нет |
| `REJECTED_NOT_WRITABLE` | Тег только для чтения (датчик) — **запись запрещена** |
| `REJECTED_TYPE_MISMATCH` | Значение не приводится к типу тега |
| `REJECTED_PROTOCOL_UNSUPPORTED` | Запись не реализована для протокола тега |
| `FAILED_NO_CONNECTION` | Нет связи с контроллером |
| `FAILED_WRITE` | Прочая ошибка записи |

Если ответ шлюза не пришёл вовремя, монитор ставит свой локальный статус `NO_CONFIRMATION`
(«результат неизвестен» — не отказ).

### 1.4. Writability — что можно менять, а что нет

Как у реального ПЛК: писать можно **команды** и **уставки**, показание **датчика** — нельзя.
И только по **OPC UA и PAC**: Modbus-контроллер (WAGO) отдаёт показания и на запись закрыт.

- Каждый тег в шлюзе несёт признак `writable` (поле `TagEntity.writable`, колонка `writable`
  в таблице `tags`, ключ `writable` в `controllers.yaml`).
- `writeTag` отклоняет запись **до похода в контроллер**:
  - Modbus-тег → `REJECTED_NOT_WRITABLE` всегда, **по протоколу, а не по флагу**: у
    holding-регистра нет признака «только чтение», и ошибка в конфиге молча перезаписала
    бы регистр прибора;
  - не-writable тег → `REJECTED_NOT_WRITABLE` (для OPC UA это ещё и экономия round-trip до
    `Bad_NotWritable`).
- Показание датчика после отказа продолжает жить своей жизнью.

**Правило** (реализовано в `tools/build_data_model.py`):

| Можно писать (OPC UA / PAC) | Только чтение |
|---|---|
| `ST` исполнительных механизмов: клапан `V`, мотор `M`, выход `DO`, регулирующий клапан `VC`, сирена `HA`, лампа `HL` | показания: `V`/`F`/`T`/`CLEVEL`/`FRQ`/`RPM`, `ST` датчиков (`DI`, `LS`, `FS`, `SB`, `TE`, `PT`, `QT`, `AI`, `FQT`) |
| режим `M` любого прибора, `CMD` линии и системы, выбор рецепта/программы | вычисляемое контроллером: `STATE`, `OPER`, рабочие параметры линии (концентрация, расход, время операции, выходы ПИД) |
| уставки `P_*` приборов, параметры станции, самоочистки, рецепта, уставочные параметры линии | статистика линии, `NODEENABLED`, строковые поля |
| — | **всё на Modbus**, даже если по смыслу это уставка |

Итог на текущем конфиге: **2031 тег** можно писать, **486** — только чтение (из них 212 Modbus).

Записанное значение **держится**: у RW-тега с источником в архиве симулятор после записи
оператора «защёлкивается» на ручном значении и архив его больше не трогает.

### 1.5. Откуда берутся значения и как поменять правило

Правило записи и источник значения каждого канала задаёт `tools/build_data_model.py`:

- **измерения** — серии архива BN1_MCA1 своей физической величины. Второй байт cid архива —
  номер подтипа в базе каналов (`2A1D…` температура, `2A63…` давление, `2A3B…` расход…);
  коды обрыва датчика (±3276.7, 32.76, 1000) выбрасываются, смещение нуля прижимается к 0;
- **производные** — из тех же серий: объём счётчика = интеграл расхода, время операции =
  возраст номера операции, задания подогрева/расхода = рецепт, пока идёт операция;
- **уставки и параметры** — наладочные константы `tools/cip_params.py` (имена и индексы из
  прошивки `ptusa_main`: `cip_tech_def.h`, `mcaRec.h`, `device.h`);
- **линии 1–3 работают, 4–6 выключены** — в архиве данные только по трём линиям.

Чтобы изменить правило:

1. Поправь нужный обработчик в `tools/build_data_model.py` (или значение в `tools/cip_params.py`).
2. Пересобери оба конфига и проверь их по всему архиву:
   ```bash
   python3 tools/build_data_model.py     # правит replay_config.yaml и controllers.yaml
   python3 tools/check_data_model.py     # минусы, диапазоны, запись, неизменность уставок
   ```
   Скрипт идемпотентен; тест `tests/test_data_model.py` падает, если конфиги не пересобраны.
3. Пересобери и подними стек (`./up.sh --build` или см. часть 3).

> ⚠️ **Колонка `writable`** — часть схемы под управлением **Flyway** (`db/migration`). На свежей
> БД создаётся автоматически (`./up.sh down -v && ./up.sh`). Дальше схему меняешь только новой
> миграцией `Vn__*.sql` — Hibernate её не создаёт (`ddl-auto=validate` лишь сверяет схему).

### 1.6. Примеры команд (проверка без монитора)

Отправить команду можно прямо в топик — формат тот же, что шлёт монитор:

```bash
# Выключить мотор по PAC (ST — целое состояние прибора: 0 стоп, 1 пуск)
echo '{"commandId":"t1","tagName":"Барановичи-1.BN1_MCA1.M_ST.LINE1M1.ST","dataType":"INT","value":0,"requestedBy":"op","timestamp":"2026-08-06T12:00:00Z"}' \
  | docker exec -i scada-kafka /opt/kafka/bin/kafka-console-producer.sh \
      --bootstrap-server localhost:9092 --topic scada-commands

# Задать уставку по OPC UA: температура щелочной мойки линии 1 (RT_PAR_F[26] = P_T_S, °C)
echo '{"commandId":"t2","tagName":"Барановичи-1.BN1_MCA1.Параметры_линии_1.OBJECT1.RT_PAR_F[26]","dataType":"FLOAT","value":80.0,"requestedBy":"op","timestamp":"2026-08-06T12:00:00Z"}' \
  | docker exec -i scada-kafka /opt/kafka/bin/kafka-console-producer.sh \
      --bootstrap-server localhost:9092 --topic scada-commands

# Прочитать результаты
docker exec scada-kafka /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 --topic scada-command-results \
  --from-beginning --timeout-ms 5000
```

Попытка записать в датчик (`…TE_V.LINE1TE1.V`) или в любой Modbus-тег (`…TE_V.LINE2TE1.V`)
вернёт `REJECTED_NOT_WRITABLE`, а датчик продолжит слать своё измерение в `scada.tags`.

## Часть 2. Нагрузочное тестирование (`loadtest/`)

Стенд гоняет **симулятор → шлюз → Kafka** под нагрузкой и пишет метрики в CSV. Монитора
в этом стенде нет — меряется сторона производства (успевает ли шлюз выдавать поток).

Ключевой факт: телеметрия шлюза — **firehose**, каждый тег шлётся каждый цикл, поэтому
поток предсказуем: `сообщений/с ≈ число_тегов / (poll_ms / 1000)`.

### 2.1. Запуск

```bash
cd loadtest
python3 run.py smoke          # дымовой: 1000 тегов ~1000 msg/s
python3 run.py stress_opcua   # лестница OPC до колена
python3 run.py stress_modbus  # лестница Modbus (последовательное чтение — узкое место)
python3 run.py wave           # спайк: симулятор то пропадает, то возвращается
python3 run.py soak           # долгая ровная нагрузка + chaos (утечки)
```

Результат: `loadtest/metrics/<профиль>_<время>.csv` + сводка по ступеням в консоли.
Профили правятся в `loadtest/profiles.yaml` (число тегов/частота/протокол/длительность).

### 2.2. Что смотреть в CSV

| колонка | смысл | на что смотреть |
|---|---|---|
| `produced_rate` | реальный поток в Kafka, msg/s | главный показатель |
| `achieved_pct` | % от ожидаемого | **падает ниже ~90% → колено** (шлюз не успевает) |
| `heap_mb` | heap шлюза | на soak: **не возвращается после GC → утечка** |
| `threads`, `gc_*` | потоки и сборки мусора | рост без спада — тоже признак утечки |

Где ждать стену: **Modbus** первым (1877+ тегов читаются последовательно, 1 round-trip/тег,
в один поток) → затем OPC UA (батч `read()`) → затем Kafka (одна нода).

Подробности и внутреннее устройство — в [`loadtest/README.md`](../loadtest/README.md).

## Часть 3. Запуск стека и окружение

Единый стек (postgres + kafka + симулятор + шлюз) — одной командой:

```bash
./up.sh            # собрать jar (если надо) + поднять стек
./up.sh --build    # пересобрать образы (после правок кода/конфигов)
./up.sh --logs     # то же + логи шлюза
./up.sh down       # остановить (данные БД сохранятся)
./up.sh down -v    # остановить + стереть БД
```

Порты на хост: шлюз `8888` (actuator), Kafka `9094`, Postgres `5433`, симулятор `4840`/`5020`.

**Окружение (Fedora):** рабочий бэкенд — нативный **podman**; `up.sh` сам поднимает
`podman.socket` и ставит `DOCKER_HOST`, после чего `docker`/`docker compose` работают против
podman. SELinux Enforcing — bind-mount конфигов метится `:Z`.

**Флаги шлюза** (`application.yaml → gateway`, меняются без пересборки, через env — перезапуск):

| Флаг | env | По умолчанию | Смысл |
|---|---|---|---|
| `gateway.persist-telemetry` | `GATEWAY_PERSIST_TELEMETRY` | `true` | писать телеметрию в БД шлюза (в Kafka идёт всегда) |
| `gateway.alarms.enabled` | `GATEWAY_ALARMS_ENABLED` | `false` | считать алармы в шлюзе (по умолчанию их считает монитор) |
| `gateway.send-bad-frames` | `GATEWAY_SEND_BAD_FRAMES` | `false` | слать кадр при обрыве (`value=null, quality=BAD`) |

> Имя env для флага с дефисом (`persist-telemetry`) — `GATEWAY_PERSIST_TELEMETRY`
> (`.`/`-` → `_`): флаги читаются через `@Value`, а не relaxed binding.
