## [Unreleased]

### Добавлено
- **Пользовательские скрипты обработки значений** (Lua, `gateway.scripts.*`). Папка
  `SCADA-gateway/scripts/`: `scripts.yaml` привязывает скрипт к каналам по маске имени с
  параметрами; `process(value, quality, ctx)` обрабатывает каждое снятое значение до Kafka,
  истории и алармов, необязательная `write(value, ctx)` пересчитывает команду оператора для
  ПЛК. Цепочки, состояние канала между вызовами (`ctx.state`), подхват правок без перезапуска
  (сломанная версия не применяется), песочница с лимитом времени, `GET /api/scripts`, метрика
  `scada_script_errors_total`. Примеры: `sensor_break.lua`, `scale.lua`, `deadband.lua`.
- **Горячее резервирование шлюза** (`gateway.ha.*`, по умолчанию выключено). Два экземпляра
  на одних топиках; активный выбирается через группу Kafka (`ha/LeaderElector`), резервный
  держит соединения с ПЛК и опрашивает их, но в Kafka не публикует, историю не пишет и
  команды не исполняет. Переключение на стенде: падение активного — 2,1 c, штатная остановка —
  0,35 c; перезапущенный резерв лидерство не отбирает (CooperativeStickyAssignor), отрезанный
  от брокера активный сам уходит в резерв. `docker-compose.ha.yml` — пара на стенде,
  `GET /api/ha`, метрика `scada_ha_active`, событие `HA` в журнале и `scada-events`.
- Команды старше `gateway.commands.max-age-ms` (30 c) не исполняются — новый статус
  `REJECTED_EXPIRED`. Раньше после перезапуска шлюза консьюмер продолжал с сохранённой позиции
  группы и отправлял в ПЛК команды, накопившиеся за простой (`auto-offset-reset: latest`
  действует только для новой группы).
- `up-moika.sh` (стенд на эмуляторе мойки одной командой; режим `plc` — только прошивка и фасад),
  `docs/MONITOR_INTEGRATION.md` и готовая замена `docker-compose.gateway.yml` монитора
  (`docs/monitor/`). Проверено из свежего клона ветки: весь стенд — одной командой за ~30 с, и
  режим «шлюз на хосте» (как в `start-all.ps1`) — 1834 канала, команда записи `APPLIED`.
- **Станция целиком по OPC UA через эмулятор мойки.** Встроенный OPC UA-сервер ptusa отдаёт
  только `state/value` (22 % каналов, запись на прибор не действует), поэтому добавлен
  **OPC UA-фасад `ptusa-opcua/`**: берёт у настоящей прошивки весь снимок driver-master
  (объекты, уставки, режимы, SYSTEM) и отдаёт узлами OPC UA `ns=2;s=<прибор>.<поле>`; запись
  клиента — команда прошивке, её код результата — статус записи; нет связи — все узлы
  `BadCommunicationError`. `docker-compose.moika.yml` — стенд: прошивка + фасад + шлюз, без
  Python-симулятора. Тесты фасада — `ptusa-opcua/tests` (фейковый PAC), job в CI.
- **Конфиг реальной станции** `config/stations/BN1_MCA1.yaml`: один контроллер, все каналы по
  OPC UA (`PROTOCOL=pac` — прямой PAC). Генератор `tools/station_config.sh` строит его из базы
  каналов (`.cdbx`) и проекта ПЛК (EasyEPLANner) кодом импорта монитора — ключи совпадают с
  объектной базой каналов монитора; каналы объектов, которых нет в проекте ПЛК, выключены.
  **На запись открыты все числовые каналы** (1816 из 1834; `WRITABLE=rules` — только команды и
  уставки по `writable-rules.tsv`). На стенде с настоящей прошивкой, сквозным прогоном через
  Kafka: 1834/1834 каналов GOOD; запись в каждый из 1812 числовых каналов — 1812/1812
  `APPLIED`, значение изменилось у 1668 (у 144 его пересчитывает программа ПЛК); встроенный
  конфиг стенда находил 1264 из 2517.
- `CONTROLLERS_CONFIG` — внешний файл контроллеров без пересборки образа (по умолчанию —
  встроенный конфиг стенда).
- **Модель данных станции** (`tools/build_data_model.py`): у каждого из 2517 каналов задан
  источник значения и право записи. Измерения берут серию архива BN1_MCA1 своей физической
  величины — второй байт cid архива оказался номером подтипа в базе каналов, все 20 групп
  сопоставлены однозначно. Производные величины считаются из тех же серий (объём — интеграл
  расхода, время операции — возраст номера операции, задания — рецепт на время мойки).
- **Уставки и параметры по прошивке ptusa** (`tools/cip_params.py`): имена и индексы
  `PAR_MAIN`, `RT_PAR_F`, `REC_PAR`, `PAR_SELFCLEAN` из `ptusa_main`, наладочные значения
  согласованы с архивом.
- **Проверка адекватности по всему архиву** (`tools/check_data_model.py`): по всем точкам
  серий, а не по окну Kafka — знак, физические диапазоны, 0/1 дискретов, монотонность
  счётчиков, неизменность уставок, право записи. Тесты `tests/test_data_model.py`.
- `ReplaySpec` в симуляторе: фильтр кодов обрыва датчика, порог, масштаб, обрезка,
  режимы `integral` и `age`.
- `tools/ptusa_emulator.sh` — эмулятор настоящего PAC (прошивка ptusa_main под ПК с проектом
  станции) для проверки протокола; `PacConnectionIT` гоняется и против него, и против
  симулятора, и сверяет PAC-теги `controllers.yaml` с контроллером.

### Исправлено
- Синхронизация `controllers.yaml` с БД — одной транзакцией под advisory-локом. Раньше
  `@Transactional` на `@PostConstruct` не действовал (вызов мимо прокси) — каждая строка
  коммитилась отдельно, а два экземпляра на общей БД падали на UNIQUE при одновременном старте.
- OPC UA-клиент шлюза ходит по адресу **из конфига**, а не по тому, что сервер анонсирует при
  discovery (хост и порт endpoint подменяются, `EndpointUtil.updateUrl`). Раньше за Docker/NAT
  шлюз подключался к недоступному имени; теперь `OPCUA_ENDPOINT` сервера на подключение не влияет.
- Опрос OPC UA: если **все** узлы контроллера вернули BAD, связь считается потерянной
  (`DISCONNECTED`). Раньше пер-узловые BAD-статусы связь не роняли, и при сервере, у которого
  пропала шина или рантайм (`BadCommunicationError` на всех узлах), значения замирали на
  мониторе при «живой» связи и без единой строки в журнале.
- **PAC: протокол как у настоящего ptusa** (сверено с эмулятором 2026.4.2.1). Шлюз принимает
  приветствие `PAC accept` (раньше читал его как заголовок ответа и не подключался), берёт
  значение из снимка `t[deviceName][fieldName]` вместо выдуманной таблицы `tags[channelId]`
  (поля-массивы `RT_PAR_F[12]`, строки) и проверяет код результата записи — команда, которую
  PAC не выполнил, теперь `FAILED_WRITE`, а не `APPLIED`. Симулятор отдаёт тот же формат.
- Lua от контроллера исполняется в урезанном стейте LuaJ — без `io`, `os`, `luajava` и
  чтения файлов.
- **Ответ PAC больше не может повесить шлюз.** Раньше Lua-снимок исполнялся без лимитов:
  бесконечный цикл вешал поток опроса навсегда вместе с блокировкой соединения PAC, за которой
  встают все команды (консьюмер последовательный); `loadstring(string.dump(...))` собирал и
  исполнял байткод, который Lua не проверяет (выход из песочницы); `string.rep` съедал память JVM;
  zlib-бомба из одного кадра (≤ 64 КБ) раздувалась в десятки МБ до исполнения. Теперь: потолок
  распакованного ответа 8 МБ, из стейта убраны `load`/`loadstring`/`string.dump`/`pcall`/
  `collectgarbage`, лимит времени 1 с на ответ, `string.rep` ≤ 1 МБ; превышение рвёт соединение,
  каналы получают BAD, опрос переподключается. Проверено на настоящей прошивке: 1834/1834 каналов
  читаются (разбор снимка 1–5 мс при лимите 1000 мс).

### Изменено
- **Запись только по OPC UA и PAC, только команды и уставки.** Шлюз отклоняет Modbus
  по протоколу (`REJECTED_NOT_WRITABLE`), даже при `writable: true`; показания датчиков,
  вычисляемые значения и статистика — только чтение. 2031 канал RW, 486 RO.
- Серии архива чистятся, а не выбрасываются: коды обрыва (±3276.7, 32.76, 1000) заменяются
  последним нормальным значением, смещение нуля прижимается к 0. Линии 1–3 работают,
  4–6 выключены (данных в архиве по ним нет).

### Удалено
- Запись по Modbus в шлюзе (`writeModbus`, `ModbusClientService.writeRegister/writeFloat`).
- `tools/enable_replay.py` и `tools/mark_writable.py` — заменены моделью данных.

## [0.1.0] — 2026-09-01

Первый размеченный релиз шлюза сбора данных.

### Добавлено
- Двухпротокольный сбор одновременно: **OPC UA** (Eclipse Milo) + **Modbus TCP** (j2mod),
  2471 канал из общей базы (`tagId = node.id`).
- Публикация в **Kafka**: телеметрия (`scada.tags`), алармы (`scada-alarms`), события
  (`scada-events`); приём команд записи (`scada-commands` → `scada-command-results`).
- Объектная модель прибора: монитор восстанавливает device/field/type из своего реестра по ключу.
- **Надёжность:** авто-переподключение (супервизор + токен поколения против flapping),
  таймауты OPC UA/Modbus, журнал `event_log`, edge-триггерные алармы (флаг, по умолчанию OFF).
- **Наблюдаемость:** метрики Prometheus на `/actuator/prometheus`.
- **Схема БД под Flyway** (`ddl-auto=validate`); PLC-симулятор (Python) с проигрыванием
  5-суточного архива `BN1_MCA1`.
- **CI/CD** (GitHub Actions): сборка + тесты на каждый PR, публикация docker-образа в GHCR на merge.
- **Контрактные тесты** телеметрии шлюз→монитор: unit (форма/типизация/маршрут) и
  EmbeddedKafka (реальный топик из конфига + сквозной round-trip).

### Изменено
- Декомпозиция god-класса `OpcUaClientServiceDB` (−43%): вынесены ValueCodec, CommandService
  (через порты, DIP), AlarmEvaluator, TelemetryProcessor, ModbusBatchReader и др.; 55 тестов.
- Обновление **Spring Boot 3.2.4 → 3.5.16** (off EOL, Flyway 10).
- **Ускорение:** батч-чтение Modbus (FC03 блоками, ~30 запросов/цикл вместо 1877),
  батч-чтение OPC UA (1 read на контроллер), батч-запись телеметрии, кэши NodeId/тегов.
- Идемпотентный Kafka-продюсер (`enable.idempotence`, `acks=all`), snappy-сжатие.
- Сплошная документация кода (класс/метод/поле) и синхронизация доков с кодом.
